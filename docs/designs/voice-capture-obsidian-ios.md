## Problem Statement

Capture spoken thought on an iPhone, keep recording once the screen locks, transcribe it
fully on-device, and get a markdown note into an existing Obsidian vault without retyping.

An Obsidian plugin cannot do this: Obsidian mobile runs in a Capacitor WebView with no path
to CoreML. The deliverable is a standalone iOS app.

Three things changed from the source spec during design:

1. **The app never writes into the vault.** It owns its transcripts; handoff is a
   user-initiated share. One tap per note plus Obsidian's own destination step.
2. **Transcription runs during capture, not after it.** This is what makes (1) survivable.
3. **Stop keeps the engine tap running and takes a background task** until the tail chunk
   is transcribed and the markdown rendered. This closes the post-Stop background problem
   without depending on a deferred-processing API that a Lock Screen Stop could not submit.

## What Makes This Cool

You talk, and a well-formed markdown note exists. On a phone, in a pocket, with the radios
off. The only network activity in the app's life is one model download on first launch.

## Constraints

- **ON-DEVICE ONLY — hard, non-negotiable.** No cloud ASR. The only permitted network
  activity is the one-time model weight fetch (DNS + TLS + CDN redirect + resumable
  download; "one call" is shorthand, not literal).
  - *This is a values decision and the doc says so.* `SFSpeechRecognizer` does expose
    `requiresOnDeviceRecognition`, so the exclusion is not forced by the platform.
    **Price, recorded so a future reader knows it was seen:** a large first-run download,
    the CoreML/ANE memory and thermal gate, the chunking and overlap-merge machinery, and
    the whole M0 spike. The decision stands; owning the instrument is the project.
  - Fallback if M0 fails: see *M0 failure policy* — it is a stop, not a substitution.
- Personal tool. One user. No App Store.
- **Language coverage is a hard criterion**, stated alongside on-device-only: European
  languages including the Nordics. Parakeet v3 covers the **24 EU official languages plus
  Russian and Ukrainian** — which means **Norwegian and Icelandic are NOT supported**, since
  neither country is in the EU. Swedish, Danish and Finnish are. This is structural, so a
  point release will not fix it. Swedish/English is the primary case and is covered; if
  Norwegian is ever required, Parakeet cannot serve it and the only alternative is Whisper,
  which detects one language per ~30 s window and so degrades exactly the mid-note
  code-switching this app exists to capture.
- No editing step **in this app**. Obsidian's share target has its own destination-and-review
  step; out of our control, accepted.
- **Recording must continue with the screen locked.** Whether it can also *start* from a
  locked screen is contested and is an M0 spike — see Entry and exit below.
- **Target iOS 26.** Device is an A18 (iPhone 16 class); iOS 26 shipped a year ago, so this
  is near-certainly already true — **verify and record the actual version.**

| Floor | Source | Needed for |

### Entry and exit: contested, and an M0 spike

Revision 3 first claimed flatly that iOS cannot start recording from a locked screen. **That
over-claimed.** Review pushed back with three points that hold up:

- `AudioRecordingIntent` is documented as an intent that **starts**, stops, or otherwise
  modifies recording state — not one restricted to an already-established session.
- **App Intents declared in the app target run in the app's process**; the system launches
  the app in the background to execute them. The widget-extension-process objection applies
  only to intents declared in the *extension* target.
- Shipped third-party prior art appears to do locked-screen capture start on iOS 26
  (`philster/wake-capture-ios`, `gakonst/nanocodex` PR #428).

Against that, Apple documentation and forum reports do say recording cannot be initiated
from a fully backgrounded state. **Both readings are live. This is an M0 spike, not a
settled finding:**

> Does a `ControlWidget`-hosted intent conforming to `AudioRecordingIntent` +
> `LiveActivityIntent` start capture from the locked screen on this device and OS build?

**Design, with the preferred path first:**

- **Start (preferred, pending spike):** Lock Screen / Control Center / Action Button →
  app-target intent conforming to `AudioRecordingIntent` + `LiveActivityIntent` → capture
  starts without foregrounding.
- **Start (fallback if the spike fails):** the intent **foregrounds the app** and starts
  there. Raise phone → Face ID → one press → recording. *Face ID is required because
  foregrounding an app requires an unlocked device* — not because the intent touches the
  microphone.
- **Continue:** `UIBackgroundModes: audio` covers the locked screen while audio I/O runs.
- **Stop:** Lock Screen / Live Activity control invoking `AudioRecordingIntent` against the
  running session. No unlock needed.

**A Live Activity is mandatory, not optional.** On iOS 26 an intent conforming to
`AudioRecordingIntent` must start and maintain a Live Activity for the duration of the
recording, or **the system stops the recording.** Revision 3 correctly noted that ActivityKit
does not *grant* background runtime, then wrongly concluded no Live Activity was needed
anywhere. ActivityKit is a precondition of the intent-driven path, and it doubles as the
UI channel for everything this design promises to surface while locked.

## Premises

1. **(HYPOTHESIS — this is what M0 measures, not a premise.)** Parakeet v3 has throughput
   headroom on an A18. FluidAudio reports ~110x real-time for *batched* ASR on M4 Pro;
   single-stream RTF on a thermally limited phone is a different measurement, and the
   ~35 vs ~38 TOPS comparison is INT8 marketing throughput that says little about a
   memory-bandwidth-bound TDT decode loop. M0 keeps **four gates**: speed, memory, thermal,
   and battery.
2. **There is no language hint.** Detection is strictly automatic across 25 European
   languages including Swedish — no prompt prefix, no flag, no parameter. Mid-note
   code-switching artefacts are a v1 limitation. *Closes source spec §11 #4.*
3. **Floors as tabulated; target iOS 26.** *Closes source spec §11 #1.*
4. ~~The vault write path is the highest-severity unproven component.~~ **DISSOLVED** — no
   write path exists.
5. **Audio retention is load-bearing.** The recording is the only recovery path for a bad
   transcript. Generous default, explicit purge.
6. ~~Coordinated reads materialize iCloud placeholders.~~ **DISSOLVED** — no file provider.
7. **Post-Stop execution needs a running I/O unit AND a background task. An "active"
   session alone is not enough.** Revision 3 claimed `setActive(true)` holds the assertion
   and the app chooses when to deactivate. **That is wrong.** The execution assertion is
   held by `mediaserverd` only while the app is *actively playing or recording* — while a
   running I/O unit is moving frames. Apple's Audio Session Programming Guide says to
   deactivate when not actively recording, and explicitly says to *"use a background task
   instead of streaming silence to keep the app from being suspended."* The existence of
   `AVAudioSession.InterruptionReason.appWasSuspended` is the same fact from the other side.
   Worse here than in the general case: Stop arrives from the Lock Screen with the app
   already backgrounded, so nothing stands between it and suspension mid-inference.

   **Two mechanisms, both required, cheap and orthogonal:**
   - **Keep the `AVAudioEngine` tap running past Stop, discarding buffers.** Stop means
     "stop appending to the WAV," not "stop the engine." Only at state `ready` do
     `engine.stop()` and `setActive(false, options: .notifyOthersOnDeactivation)`.
     *Booked consequence:* the orange mic indicator and the recording Live Activity stay lit
     for several seconds after the user presses Stop. User-visible, needs a line of UI
     explanation, and will otherwise read as a bug during criterion 2 and 6 testing. It also
     burns mic power for the tail.
   - **`UIApplication.beginBackgroundTask(withName:expirationHandler:)` taken at Stop,
     before tearing anything down.** This is the mechanism Apple names, it is legal from a
     backgrounded-but-running app, and it yields on the order of 30 s (`backgroundTimeRemaining`
     is the only truth) — comfortably more than a ~6 s tail. The expiration handler persists
     the job as `captured` so the next launch finishes it.

   **`BGContinuedProcessingTask` is removed from this design entirely.** It likely requires
   foreground submission, which a Lock Screen Stop cannot provide, so it could never fire in
   the one case it was named for. The real fallback is already designed: the job stays
   `captured` and resumes on next foreground. *Also carried forward:* Live Activities do not
   *grant* background runtime — but see the entry/exit section, where one is nonetheless
   mandatory for the intent-driven path.

   **Edge cases this still does not survive, and the background task is the only cover:**
   an interruption or another app seizing the session during the tail window tears the
   session down mid-chunk. Recovery unit is the **whole chunk**, re-run on resume — see
   Reviewer Concerns on resumable-mid-chunk inference.

## Approaches Considered

### Handoff mechanism

- **A — Files-visible inbox.** *Rejected as primary: several taps, easy to defer. The two
  Info.plist keys are retained as a recovery affordance.*
- **C — `obsidian://new` deep link.** *Rejected as primary: undocumented URL length ceiling
  (~2000 chars safe; a 20-minute transcript is ~20,000), failing silently on the long
  recordings most worth keeping. Retained in the fallback tree below.*
- **D — Export protocol over A and B.** *Rejected as over-build for one user.*

**B — Share sheet (CHOSEN).** `ShareLink` hands Obsidian a **file URL to a real on-disk `.md`
file**. Handing over `Data` or a `String` loses the filename and may route the receiving
extension down a different branch.

- Effort S/M (human ~4 hrs / CC ~25 min). Risk Low.
- Pros: one tap; the app never needs to know the vault's shape, path, or sync state; no
  bookmark, no `NSFileCoordinator`, no collision handling, no conflict files.
- Cons: one note per share, no batch; Obsidian owns a destination-and-review step.
- **Type declaration is load-bearing.** `net.daringfireball.markdown` is a *third-party* UTI,
  not system-declared. Without a `UTImportedTypeDeclarations` entry (conforming to
  `public.plain-text`, extension `md`) a `.md` file URL resolves to a dynamic UTI or
  `public.plain-text` and you get a different share branch than intended. Verify the resolved
  type on the `NSItemProvider` before shipping.
- **Evidence — confirmed on device 2026-09-21: a shared `.md` becomes a NOTE, not an
  attachment.** This was the review's sharpest doubt about the chosen approach (share
  extensions commonly import files as attachments) and it is now dead. Obsidian's
  `NSExtensionActivationRule` accepts a markdown file and routes it to note creation.
  **Two narrower gaps remain:** whether YAML frontmatter survives byte-for-byte, and whether
  `ShareLink` from our app — a different `NSItemProvider` payload than Files hands over —
  hits the same branch. Both are in The Assignment.

**Fallback tree.** Branch 1 (file URL + declared markdown UTI → note) is **confirmed** and
is the shipping path. The attachment branch is deleted. Two narrow contingencies remain,
built only if The Assignment turns them up:

- If frontmatter is stripped → move metadata into the body as a bullet block.
- If `ShareLink`'s payload behaves differently from Files' → share as
  `UTType.utf8PlainText` with the body inline.

`obsidian://new` stays rejected. It was only ever the escape hatch for "no route produces a
note," and that case no longer exists.

### Inference scheduling

- **Record-then-transcribe** (source spec). *Rejected: guarantees the post-Stop problem.*
- **Incremental during capture (CHOSEN).** Inference runs on VAD segments as they close,
  legitimately covered by the audio background mode. At Stop only the tail remains, and the
  session stays up until it is done.

## Recommended Approach

```
[Action Button / Control → foregrounds app] → AVAudioSession .record activated
  → AVAudioEngine tap → 16 kHz mono Int16 WAV segments on disk (durable)
  → Silero VAD proposes boundaries
  → INCREMENTAL Parakeet inference on the ANE as segments close, fed to
     FluidAudio's SlidingWindowAsrManager 12 s at a time (a FEED size, not an
     overlap: the library owns overlap and returns token timings already
     mapped onto the whole recording's timeline)
  → [Stop via AudioRecordingIntent from Lock Screen]
     → beginBackgroundTask() taken FIRST
     → engine tap KEEPS RUNNING, buffers discarded (stop = stop appending to WAV)
  → tail chunk transcribed → markdown rendered → job state `ready`
  → engine.stop() → setActive(false, .notifyOthersOnDeactivation) → endBackgroundTask()
  → [user taps Share] → ShareLink (file URL, declared md UTI) → Obsidian
```

**Feed rule.** Audio goes to `SlidingWindowAsrManager.transcribeChunk(_:isLastChunk:)` in
12 s slices, straight through with no overlap, `isLast` on the final slice so it flushes.
Two layers of window logic would fight, so there is deliberately only one.

~~**Overlap merge.**~~ **DELETED.** We wrote a token-alignment merge before discovering
FluidAudio already does this, and better — it owns the seams and returns timings on the
global timeline. Reuse ladder: stop at the first rung that holds. Roughly 120 lines gone,
including the only algorithm in the project with no test.

**On-disk format: Int16.** 16 kHz mono Float32 is 64 KB/s ≈ 3.84 MB/min ≈ 77 MB per
20-minute note; Int16 halves it to ~1.92 MB/min with no accuracy loss, converted to Float32
at read for the model. **Refuse to start below 250 MB free; hard-abort with segment
finalization at 100 MB.** Show total store size in settings.

**Crash-safe WAV.** A RIFF header written at open carries placeholder sizes; after a
force-quit the file claims wrong length and most readers reject or truncate it. **Repair
`RIFF`/`data` chunk lengths from the on-disk file length at open** (or write headerless PCM
plus a sidecar JSON of format + frame count). Criterion 3 fails without this.

**Storage location and backup.** Audio, rendered markdown, and the job store live in
`Documents/` (which is what makes the recovery affordance work). **Set
`isExcludedFromBackupKey = true` on the audio and transcript directories**, not just the
model. Otherwise retained audio is uploaded to iCloud Backup, which contradicts both "radios
off" and the source spec's *"no audio leaves the phone, ever"* — and criterion 1 would not
catch it, because it is OS traffic, not app traffic.

**Job and state model.** A job is an ordered list of *segments*; interruptions split a
recording rather than ending it.

| State | Meaning |
|---|---|
| `recording` | Capture live; incremental inference running |
| `captured` | Audio complete; tail or backlog outstanding |
| `transcribing` | Tail running inside the still-active session |
| `ready` | Markdown rendered, awaiting share |
| `shared` | Handed to the share sheet (timestamped) |
| `failed` | Reason + retryable flag; audio always retained |

**Graded thermal policy** (replaces the source spec's flat queue pause, which under
incremental inference would grow the untranscribed tail without bound and break criterion 6
precisely when the device is hottest):

- `.serious` → drop inference to a lower duty cycle, raise the chunk cap.
- `.critical` → suspend inference, mark the job `captured`, and **visibly withdraw the
  10-second promise with a stated reason**.

**Backpressure — two thresholds, one derived from criterion 6.** If inference falls behind
capture (thermal throttle, an unbroken monologue with no VAD boundary, a competing app),
backlog grows silently — the new architecture's characteristic failure.

- **8 s backlog → the 10-second promise is withdrawn** and the Live Activity shows an
  estimate instead. Derived, not picked: at the 2× speed gate, 8 s of audio is ~4 s of work,
  and 4 s plus render must fit inside criterion 6's 10 s.
- **90 s backlog → abandon incremental inference**, mark `captured`, finish at next
  foreground.

Criterion 6 keys off the 8 s threshold. (Revision 3 had only the 90 s watermark, which meant
an 89 s backlog at Stop — ~45 s of outstanding work — was a state the design called
acceptable while criterion 6 still promised 10 seconds.)

**Audio input route.** A walking capture is likely on AirPods, and HFP input is narrowband —
that will cost more WER than the `.measurement` A/B can recover. **Prefer the built-in mic
via `setPreferredInput`**; record the actual route in the job and emit it in frontmatter.

**Microphone permission at the entry point.** The intent checks
`AVAudioApplication.recordPermission` first and fails with a visible, actionable message.
Never start a silent no-op recording.

**Interruption handling.** `.began` → finalize the current segment. `.ended` with
`.shouldResume` → open a new segment in the same job. Same for route changes.
**But resume is not guaranteed:** a backgrounded recorder interrupted by a call is commonly
suspended and may never receive `.ended`. **Specify the miss path: finalize the job from
disk at next launch, notify the user, never silently lose the second half.** Spiked in M0.

**Failure paths to handle explicitly:** model load failure; inference failure mid-chunk
(retry that chunk, keep completed ones); truncated or corrupt WAV; disk full mid-recording;
backlog watermark breach; interruption without resume.

**Post-share lifecycle.** A shared transcript keeps its markdown and audio and is marked
`shared` with a timestamp. Re-sharing is allowed but warns — Obsidian's picker will not
deduplicate and you will get a second note.

**Recovery affordance.** `UIFileSharingEnabled` + `LSSupportsOpeningDocumentsInPlace`. Two
Info.plist keys, zero code. Without them there is no route to get retained audio or rendered
markdown off the device if the share target misbehaves — and the audio is the sole recovery
path per premise 5.

**Deleted from the source spec:** §5.1 (security-scoped bookmark, document picker), §5.2
(`NSFileCoordinator`, collision suffixing, temp-file atomic move), and the stale-bookmark
and iCloud-conflict rows of §9. **The app cannot create conflict files, overwrite a note, or
leave a half-written file in the vault.** (Not "every irreversible failure mode is gone" —
**purging retained audio remains irreversible** and destroys the only recovery path. It is
the one remaining one-way operation and stays behind an explicit action.)

**Retained from the source spec:** disk-during-capture, pinned HF
revision, Wi-Fi-gated resumable model download, resumable-mid-chunk inference.

**Pin CoreML compute units to `.cpuAndNeuralEngine`.** `MLModelConfiguration.computeUnits`
defaults to `.all`, which includes the GPU — and **iPhone apps cannot use the GPU in the
background.** If FluidAudio leaves the default and CoreML schedules any part of the encoder
or the TDT decode loop on the GPU, background inference fails on exactly the locked-screen
path this whole architecture depends on. The source spec had this right and revision 3
dropped it. **M0 must verify FluidAudio exposes a way to set it — if it does not, that is a
design-level finding, not a note.** "Zero GPU work scheduled while locked" is an M0 pass
condition. Related: CPU/ML-intensive work is reported to run several times slower when
backgrounded, so the ≥ 2× speed gate must be measured *under lock*, not in the foreground.

**ActivityKit is required**, per the entry/exit section: recording intents pair with
`LiveActivityIntent`, and the Live Activity is also the UI channel for thermal withdrawal,
backlog breach, and interruption notices while the screen is locked.

**File protection.** Audio segments and job state are written continuously while locked.
Set `.completeUntilFirstUserAuthentication` explicitly on the audio, transcript, and
job-store directories — anything at `.complete` makes every write after lock fail and
silently loses audio from the first lock onward. Privacy consequence, booked next to the
backup-exclusion decision: retained audio is readable after first unlock, and
`UIFileSharingEnabled` puts it in Files.

**Implementation specifics.** `NSMicrophoneUsageDescription`; `UIBackgroundModes: audio`;
`UNUserNotificationCenter` authorization (for the next-launch interruption miss path);
Silero VAD ships with FluidAudio (not separately converted — **verify in M0**, this is
asserted flatly while every sibling API fact is marked verify);
`FluidInference/parakeet-tdt-0.6b-v3-coreml` on Hugging Face at a **pinned commit SHA**,
stored in Application Support with `isExcludedFromBackupKey = true` and resumable download.
**Artifact size is unverified** — the source spec says ~460 MB, but 0.6B parameters is
~1.2 GB at FP16 and ~600 MB at INT8, so 460 MB implies aggressive quantization that also
affects accuracy and the memory gate. **Record the real size at the pinned SHA as M0's first
output.**

**Note format** (inlined from source spec §5.4, since Next Steps depends on it):

```markdown
---
created: 2026-09-21T14:32:00+02:00
duration: 4m12s
language: [sv, en]          # omit entirely if AsrManager does not return it
input_route: built-in
model: parakeet-tdt-0.6b-v3
model_revision: <pinned-sha>
tags: [voice]
---

<transcript>
```

Filename: `YYYY-MM-DD-HHmm-voice.md`. Raw verbatim transcript, no LLM shaping in v1.
`language` is a **list**, not a scalar — a scalar is wrong by construction for the
code-switched notes criterion 5 is built around — and is emitted only if `AsrManager`
actually returns detected language. Premise 2 establishes there is no language *input*; it
says nothing about output. Confirm in M0.

## Success Criteria

1. **No network after first launch.** Primary test: full cycle in airplane mode, completes.
   Supporting static assertion: exactly one networking call site in the codebase, nothing
   beyond `URLSession` linked. Then check iOS Settings → Privacy → App Privacy Report after
   a week. *(A Charles proxy cannot attribute traffic to one app, needs its root CA trusted,
   misses non-proxied transports, and would be polluted by Obsidian's own vault sync — the
   source spec's Charles plan is weaker than it looks.)*
2a. **Recording continues 20 minutes with the screen locked, uninterrupted**, with Stop
   issued from the Lock Screen control.
2b. **An incoming call is either resumed into the same job, or recovered losslessly as a
   split job with the user notified.** Which of the two ships is decided by M0 step 5.
   (Revision 3 folded these together, so implementing the miss path looked like it satisfied
   a criterion that actually demanded uninterrupted continuation.)
3. **Force-quit mid-recording loses no audio**; the job resumes from disk with a readable WAV.
4. **Seam correctness.** We no longer own a chunker, so this no longer tests our code. It
   becomes an acceptance check on the library: feed the fixture in 12 s slices and assert the
   transcript has no duplicated or dropped 3-gram at a slice boundary. If it does, that is a
   FluidAudio issue to report, not ours to patch. Normalisation as before:
   normalized word-level edit distance ≤ 2% (lowercase, strip punctuation, collapse
   whitespace, whitespace-tokenize, denominator = baseline token count), and **no 3-gram
   duplicated or dropped at a seam that is not present in the baseline at the same
   position** — natural speech repeats itself, so a bare "zero duplicated 3-grams" is a
   false-positive generator.
5. **Code-switching, falsifiable:** a human reader reconstructs the intended meaning of every
   paragraph of the Swedish/English fixture **without hearing the audio**. **Use a second
   reader, or run it at least two weeks after recording** — the person who spoke it will
   reconstruct from memory, not from the text.
6. **At Stop, state reaches `ready` within 10 seconds** for a recording up to 20 minutes.
   Measured from timestamps written into the job store at Stop and at the `ready` transition
   — not a stopwatch, since the device is locked. Withdrawn visibly under `.critical` thermal
   or a backlog breach, per the graded policy.
7. **A week of real captures** with no reach for another tool.

## Distribution Plan

Personal device only. No App Store, so the privacy label and review process are moot — keep
the privacy posture anyway; it is the point of the project.

**AGPL is kept out by commitment, not interpretation.** vox.md is AGPL-3.0, and TestFlight is
a third-party distribution channel where conveying triggers AGPL obligations. **Resolution:
vox.md is read for technique only; no code is copied.** With that held, AGPL never attaches.

**Free provisioning is viable, and is the starting position.** Revision 4 said the $99/yr
programme was required and made it M0 step 0. That was wrong — it assumed an App Group the
design no longer needs.

*What the free personal team costs you:* certificates expire every **7 days**; **3 apps
installed at a time**; roughly **10 App IDs per 7 days** (an app + widget extension is 2);
no push notifications; **no App Groups**; no TestFlight. Local notifications work.

*The one that nearly blocked this design:* **App Groups need a paid account.** They were in
the plan so a `ControlWidget`'s value provider — which runs in the widget extension process
— could read recording state. **Resolved by dropping the stateful control:** use a stateless
`ControlWidgetButton` that fires the intent, and let the **Live Activity** display state.
ActivityKit passes `ContentState` through the system, not through an App Group, and local
`Activity.update()` needs no APNs. The Live Activity is already mandatory for the
`AudioRecordingIntent` path, so this removes a component rather than adding one.
**Verify at M0** that Live Activities and a widget extension both sign under a free personal
team — treated as unverified like every other platform claim here.

*The 7-day expiry against criterion 7 (a week of real captures):* re-sign from Xcode once
mid-week, or use SideStore, which after a one-time computer setup refreshes on-device via a
pairing file and a local VPN — no laptop on the network. Either makes the week achievable.

**What $99/yr would actually buy:** 1-year signing (no weekly refresh), App Groups, push,
TestFlight. None of those are needed by this design. **Start free; pay only if the weekly
refresh annoys you more than the fee does, or if M0 turns up a capability that needs it.**

No CI/CD; local Xcode builds.

## Reviewer Concerns

Three adversarial review rounds ran against this document (5/10 → 7/10 → 6/10). The score
fell in round 3 because the doc became specific enough for platform claims to be checked
against Apple documentation — and two were wrong. Round 3's three design-breaking findings
are applied above. These remain open, carried deliberately rather than missed.

**Needs a decision before M1**

1. ~~Fallback tree branches 2–4 are specified but scheduled nowhere.~~ **RESOLVED
   2026-09-21.** Confirmed on device that a shared `.md` becomes a note, so the attachment
   branch and the `obsidian://new` escape hatch are deleted. Two narrow contingencies
   remain, explicitly marked as contingency.
2. **Model download has no free-space guard** (the recording path has one at 250 MB), and no
   stated behaviour if a first capture is attempted before the download completes.
3. **`.serious` thermal policy has no numbers.** "Lower duty cycle, raise the chunk cap"
   is not implementable, and both values determine whether the 8 s backlog threshold trips.
   Suggested: 50% duty cycle, cap 12 s → 30 s, which grows backlog at 0.5× real time and
   trips the promise threshold after ~16 s of continued speech.
4. **The battery gate has no threshold** inside a four-gate structure whose failure mode is
   a project stop. Suggested: ≤ 15% for a 20-minute locked capture with inference, and
   ≤ 2.5× the inference-disabled baseline. Revise once measured.

**Unspecified mechanisms**

5. **"Resumable-mid-chunk inference"** is retained from the source spec and never specified,
   while being the recovery path for suspension and jetsam mid-tail. Premise 7 now states the
   recovery unit is the whole chunk, re-run on resume. Either specify true mid-chunk resume
   or delete the claim from the retained list — the chunk-level answer is probably what you
   want anyway.
6. **Float32 → Int16 conversion is unspecified.** Use `clamp(-1, 1) × 32767`. Also drop the
   "no accuracy loss" phrasing — it is quantization, immaterial to WER but not lossless.

**Verification hardening**

7. **Criterion 1's static assertion is call-site-based.** Also assert against
   `Package.resolved`: no third-party network or analytics package in the resolved graph.
8. **The `.md` UTI analysis covers what we export; the binding constraint is what Obsidian's
   share extension declares it accepts** (`NSExtensionActivationRule`). That is what
   Assignment step 3 actually tests — name it as such. Conform the imported declaration to
   both `public.plain-text` and `public.text`.

**Cosmetic**

9. Premise 1 is labelled "not a premise" and sits under Premises. Approaches run A, C, D, B,
   with D forward-referencing a B introduced later.
